### A1 · 13.4.1 Agent 多轮工具调用 —— 返回结构与 SDK 风格都不对

**方案原文（p134）**：

```python
MAX_TOOL_ROUNDS = 12
for _round in range(MAX_TOOL_ROUNDS):
    resp = await call_llm(messages, system=system, temperature=0.3,
                          max_tokens=3000, tools=AGENT_TOOLS)
    tool_uses = [b for b in resp.content if b.type == 'tool_use']
    if not tool_uses:
        break
    for tu in tool_uses:
        result = execute_tool(tu.name, tu.input, user, db)
        messages.append({'role':'user','content':[{'type':'tool_result',
                                                   'tool_use_id': tu.id, 'content': result}]})
```

**问题（4 处，任一处都跑不通）**：

1. `resp.content` / `b.type` / `tu.name` —— 这是 **Anthropic 官方 SDK 的对象风格**。本项目 `call_llm` 返回的是 **dict**，必须 `resp.get("text")`、`resp.get("tool_calls")`。照抄会在第一轮就 `AttributeError: 'dict' object has no attribute 'content'`。
2. **缺少 assistant 消息回写**。工具调用必须先把 `role=assistant` 的 `tool_use` 消息 append 进 messages，再 append `tool_result`。方案直接跳到最后一步，多数 LLM 网关会报 400（`tool_result` 找不到对应的 `tool_use_id`）。
3. **漏了 `stop_reason` 判断**。实际是 `if not tool_calls or stop_reason != "tool_use": break`，只判 `tool_calls` 会在模型「既要回答又要调工具」时误判。
4. 漏了 `_run_tool` 的异常兜底与 `result_str[:4000]` 截断（超长结果会把上下文撑爆）。

**真实代码**（`routers/chat.py:515-552`）：

```python
for _round in range(MAX_TOOL_ROUNDS):
    resp = await call_llm(
        messages, system=system, temperature=0.3,
        max_tokens=3000, tools=AGENT_TOOLS,
    )

    text_part = resp.get("text", "")
    tool_calls = resp.get("tool_calls", [])
    stop_reason = resp.get("stop_reason", "")

    if not tool_calls or stop_reason != "tool_use":
        final_answer = text_part
        break

    assistant_content = []
    if text_part:
        assistant_content.append({"type": "text", "text": text_part})
    for tc in tool_calls:
        assistant_content.append({
            "type": "tool_use", "id": tc["id"],
            "name": tc["name"], "input": tc["input"],
        })
    messages.append({"role": "assistant", "content": assistant_content})

    tool_results_content = []
    for tc in tool_calls:
        result_str, _ok = await _run_tool(tc["name"], tc["input"], user.id)
        tool_actions.append({
            "tool": tc["name"], "input": tc["input"],
            "result": result_str[:500],
        })
        tool_results_content.append({
            "type": "tool_result", "tool_use_id": tc["id"],
            "content": result_str[:4000],
        })
    messages.append({"role": "user", "content": tool_results_content})
else:
    final_answer = final_answer or "操作已完成（达到最大轮次）。"
```

> 另注：实际有**两套循环**——非流式（`:515`，上面这段）和流式（`:632`，`call_llm_stream`，用于 SSE 逐字输出）。方案只给一套，若想体现工程完整度，可补一句「另有一份流式实现，逻辑同构」。

### A3 · 13.5.1 OpenAPI 鉴权 —— 不是依赖注入

**方案原文（p135）**：

```python
WEBHOOK_KEY = 'docfusion-webhook-2026'
def verify_api_key(x_api_key: str = Header(...)):
    if x_api_key not in (WEBHOOK_KEY, SECRET_KEY):
        raise HTTPException(401, 'invalid api key')
    return True
router = APIRouter(prefix='/api/open', dependencies=[Depends(verify_api_key)])
```

**问题（3 处）**：

1. **`router` 上没有 `dependencies`**。实际 `APIRouter(prefix="/api/open", tags=["开放API"])`，鉴权是**每个端点内手动调 `_auth(x_api_key)`**。
2. **函数名与签名不同**：实际 `_auth(api_key: Optional[str])`，普通函数，不是 `Depends` 依赖。
3. **错误码语义不同**：方案统一 401；实际「缺少 key」→ 401、「key 无效」→ **403**。这个区分是对的（缺凭证 vs 凭证错），方案反而写粗了。

**真实代码**（`routers/openapi.py:31-44`）：

```python
router = APIRouter(prefix="/api/open", tags=["开放API"])

WEBHOOK_KEY = "docfusion-webhook-2026"


def _auth(api_key: Optional[str]):
    if not api_key:
        raise HTTPException(401, "缺少 X-API-Key")
    if api_key not in (WEBHOOK_KEY, SECRET_KEY):
        raise HTTPException(403, "API Key 无效")
```

**端点内调用方式**（以 `/upload` 为例，`routers/openapi.py:52-55`）：

```python
@router.post("/upload")
async def upload(file: UploadFile = File(...), x_api_key: Optional[str] = Header(None)):
    _auth(x_api_key)
    ...
```

> 建议：这段要么按实际写「逐端点显式校验」，要么在正文补一句「早期版本用 `APIRouter(dependencies=...)` 统一注入，后改为端点内显式调用，便于对不同端点做差异化鉴权」。后者更容易被追问，推荐前者。

### A4 · 13.5.2 MCP JSON-RPC 派发 —— 返回值缺协议包装，客户端会挂

**方案原文（p135）**：

```python
async def handle_jsonrpc(req: dict, uid: int):
    method = req.get('method')
    if method == 'initialize':
        return {'protocolVersion': '2024-11-05',
                'serverInfo': {'name': 'DocFusion MCP', 'version': '1.0'}}
    if method == 'tools/list':
        return {'tools': MCP_TOOLS}
    if method == 'tools/call':
        name = req['params']['name']
        args = req['params'].get('arguments', {})
        return await dispatch_tool(name, args, uid)
```

**问题（5 处）**：

1. **返回值没有 `{"jsonrpc": "2.0", "id": rid, "result": ...}` 包装**。JSON-RPC 2.0 强制要求 `jsonrpc` 与 `id` 字段，缺了标准 MCP 客户端会直接判为协议错误。
2. **`version` 写 `"1.0"`，实际是 `"2.0.0"`**。
3. 漏了 `capabilities: {"tools": {}}`——客户端靠它判断服务端支持哪些能力。
4. **`tools/list` 不能直接返回 `MCP_TOOLS`**。内部工具定义用 `input_schema`，MCP 规范要求 `inputSchema`，中间有转换函数 `get_tools_list()`。
5. 漏了 `initialized` / `ping` 两个 MCP 握手必调方法，以及 `-32601 Unknown method` 错误分支。
6. `tools/call` 的返回值也要包成 `{"content": [{"type": "text", "text": ...}]}`，方案直接返回裸字符串。

**真实代码**（`services/mcp_service.py:433-448`）：

```python
def get_tools_list():
    return [{"name": t["name"], "description": t["description"],
             "inputSchema": t["input_schema"]} for t in MCP_TOOLS]


async def handle_jsonrpc(req: Dict, user_id: int = None) -> Dict:
    method, rid, params = req.get("method", ""), req.get("id"), req.get("params", {})
    if method == "initialize":
        return {"jsonrpc": "2.0", "id": rid, "result": {
            "protocolVersion": "2024-11-05",
            "capabilities": {"tools": {}},
            "serverInfo": {"name": "DocFusion MCP", "version": "2.0.0"},
        }}
    if method == "tools/list":
        return {"jsonrpc": "2.0", "id": rid, "result": {"tools": get_tools_list()}}
    if method == "tools/call":
        r = await execute_tool(params.get("name", ""), params.get("arguments", {}), user_id)
        return {"jsonrpc": "2.0", "id": rid, "result": {"content": [{"type": "text", "text": r}]}}
    if method in ("initialized", "ping"):
        return {"jsonrpc": "2.0", "id": rid, "result": {}}
    return {"jsonrpc": "2.0", "id": rid, "error": {"code": -32601, "message": f"Unknown: {method}"}}
```

> 这段是**最该改的之一**：方案说「完整实现 MCP 协议，可直接接入 Claude Desktop / Cursor」，但如果按方案代码实现，客户端连 `initialize` 都过不去。实际代码是对的，方案抄错了。


**问题（4 处）**：

1. **函数名不对**：仓库里只有 `applyThemeToDOM`（7 处调用）和 `applyThemeById`（5 处调用），**没有单参数的 `applyTheme(theme)`**。两者分工是「改 DOM」与「改状态 + 落盘」，方案把它们合并成了一个。
2. **参数结构不对**：实际接收的是 **colors 字典**（CSS 变量名 → 值），不是 `theme` 对象。
3. **字段名不存在**：`theme.primary` / `theme.bg1` / `theme.blur` / `theme.palette` 在仓库里零命中。
4. **`localStorage` 不在这个函数里**：实际在 `applyThemeById` 里写，key 是 `STORAGE_KEYS.active`（值确实是 `'docfusion_active_theme_id'` ✅，这点对）。

**真实代码**（`frontend/src/components/ThemeSelector.vue:383-405`）：

```javascript
const applyThemeToDOM = colors => {
  const root = document.documentElement
  Object.entries(colors).forEach(([key, value]) => {
    root.style.setProperty(key, value)
  })
  if (colors['--primary-color']) {
    root.style.setProperty('--primary', colors['--primary-color'])
    root.style.setProperty('--el-color-primary', colors['--primary-color'])
  }
  if (colors['--text-color']) {
    root.style.setProperty('--text', colors['--text-color'])
    root.style.setProperty('--el-text-color-primary', colors['--text-color'])
    root.style.setProperty('--el-text-color-regular', colors['--text-color'])
  }
  if (colors['--text-secondary']) {
    root.style.setProperty('--text-secondary', colors['--text-secondary'])
    root.style.setProperty('--text-secondary-color', colors['--text-secondary'])
    root.style.setProperty('--el-text-color-secondary', colors['--text-secondary'])
  }
  if (colors['--bg-color']) {
    root.style.setProperty('--bg', colors['--bg-color'])
    root.style.setProperty('--el-bg-color', colors['--bg-color'])
  }
}

const applyThemeById = id => {
  activeThemeId.value = id
  const theme = findTheme(id)
  applyThemeToDOM(theme.colors)
  localStorage.setItem(STORAGE_KEYS.active, id)
}
```

> 实际实现的核心价值是**变量别名映射**——一套主题变量同时喂给自定义 CSS 和 Element Plus 组件库（`--el-color-primary` 等），所以换主题时 Element Plus 的按钮、表格、标签全跟着变。方案完全没体现这一点，反而虚构了 `theme.palette.forEach` 这种不存在的逻辑。**建议按上面这段替换，并在正文点出「双变量体系」**。

## 三、建议修改（B 类，3 段）

### B1 · 13.2.1 路由守卫 —— 漏了 public 路由与登录态反向跳转

**方案**：

```javascript
if (to.path !== '/login' && !sessionStorage.getItem('token')) return next('/login')
```

**实际**（`frontend/src/router/index.ts:64-72`）：

```javascript
router.beforeEach((to, _from, next) => {
  const loggedIn = Boolean(sessionStorage.getItem('token'))
  if (to.meta.public) {
    if (loggedIn && to.path === '/login') return next('/dashboard')
    return next()
  }
  if (!loggedIn) return next('/login')
  next()
})
```

**差异**：实际按 `to.meta.public` 判定，不写死 `/login`——已登录用户访问登录页会被送去 dashboard。方案是「只拦未登录」，实际是「双向」。
**建议**：替换为实际代码。`sessionStorage` 这个细节是对的（token 存 sessionStorage 不存 localStorage），可以强调一句「关闭标签页即失效」。

### B3 · 13.7.2 鼠标跟随 —— 语义对，但实现是 Vue 组件

**方案**是裸 DOM 操作（`cursor.style.transform = ...` + `classList.toggle('cursor--hover', ...)`）。

**实际**是 Vue 组件 `frontend/src/components/CustomCursor.vue`：

```javascript
const x = ref(0)
const y = ref(0)
const isHovering = ref(false)
const enabled = ref(localStorage.getItem('docfusion_custom_cursor') !== 'false')

const cursorStyle = computed(() => ({
  transform: 'translate(' + (x.value - 16) + 'px, ' + (y.value - 16) + 'px)',
}))

const onMouseMove = e => {
  x.value = e.clientX
  y.value = e.clientY
  const target = e.target
  isHovering.value = !!(
    target.closest('button') || target.closest('a') ||
    target.closest('.clickable') || target.closest('.el-button') ||
    target.closest('.nav-item') || target.closest('.theme-item')
  )

```

**实际比方案多**：`-16px` 居中偏移、`ref` 响应式 + `computed` 驱动（不在 mousemove 里直接改 style，避免每帧触发重排）、`hovering` class 由响应式状态控制、可开关（`localStorage` 键 `docfusion_custom_cursor`）、hover 元素列表更全（多了 `.nav-item` / `.theme-item`）、`onBeforeUnmount` 清理监听。

**建议**：这段可以保留作为「概念示意」，但**必须标注「为便于理解，此处为简化示意，实际实现为 Vue 组件 + 响应式状态」**，否则同样是「代码对不上」。

这 6 段 A 类问题有共同特征，改的时候可以一并注意：
