## 二、阻断级：会直接写错数据

### N1 · 数值条件过滤把「带单位的高值行」整行误删

`services/data_filter.py::apply_numeric_filters`

原实现直接拿单元格的**数字部分**与阈值比较：

```python
num, _unit = parse_value_with_unit(row.get(col))   # "5.2万亿" -> 5.2
if not ops[op](num, threshold):                    # 5.2 > 50000 → False
```

条件「GDP 大于 5 万亿」，列头是「GDP（亿元）」，阈值换算成 50000；而行值是 `5.2万亿`，被解析成 `5.2`，于是**上海（5.2 万亿，唯一符合条件）被删掉，反而只留下写死成 `52000` 的行**。

复现（修复前）：

```
输入: [上海 5.2万亿, 北京 52000, 深圳 3.4万亿]
输出: [北京 52000]          ← 上海被误删
```

**修复**：比较前先走 `normalize_cell(value, col)`，按列头单位把单元格值换算到同一口径再比大小。修复后输出 `[上海, 北京]`。

> 这个缺陷只在「LLM 把带单位原文写进单元格」时触发，而这恰恰是叙事型 docx 数据源的常态——评测报告里 C 用例整列都是 `7.3万元`/`12.6万份` 这种写法，一旦叠加数值条件就会命中。

### N2 · 数值条件只在 LLM 兜底路径生效，结构化路径完全忽略

`routers/templates.py::_fill_table_mode`

新增的 `apply_numeric_filters` 只挂在 `_fill_table_with_llm_fallback` 里。结构化路径（数据源匹配度高、走 xlsx 直读）从头到尾没有消费 `rule_filters["numeric_filters"]`，只用了 `date_range / datetime_exact / sort / sum / stats / cities`。

后果：**同一句「GDP 大于 5 万亿」，数据源匹配得越好，条件越会被丢掉**，返回全量行；匹配得差反而筛选正确。这种「越准越错」的行为几乎不可能被用户察觉。

复现（修复前，3 列数据源走结构化路径）：条件 `GDP > 50000 亿元`，输出 4 行（上海/北京/深圳/杭州全在）。

**修复**：在结构化路径的「伪合计行清理」之后、「排序」之前，对 `rows_data`（list 与 dict 两种形态）统一套用 `apply_numeric_filters`。修复后同一用例输出 1 行（上海），日志留痕：

```
[table_fill] 数值条件生效: GDP（亿元） > 50000.0（列头单位 亿元，原条件 50000.0亿）
[table_fill] 数值条件过滤: 4 行 → 1 行（剔除 3 行）
```

### N3 · 表头写「单位：亿元」时整列不归一化

`services/unit_normalize.py::parse_header_unit`

原实现只按 `,，、;；/／` 和空白切分括号内容，`：` 不在分隔符里，于是 `GDP（单位：亿元）` 整段被当成一个片段，`split_unit("单位：亿元")` 返回 `(None, None)`，判定为「表头无单位」。

这是中文表格最常见的单位写法之一（「单位：万元」「计量单位：亿元」），命中后整列保留原始字符串、只打一条告警，用户看到的是**该列全是文本、无法求和排序**。

复现（修复前）：

```
parse_header_unit("GDP（单位：亿元）")            -> None
normalize_cell("5.2万亿", "GDP（单位：亿元）")     -> ('5.2万亿', 告警)
```

**修复**：括号内容的分隔符补上 `：:`，并剥掉「单位 / 计量单位」前缀。修复后 `-> 亿元`，`5.2万亿 -> 52000`。

## 三、高危：悄悄少数据 / 绕过本次修复

### N4 · 数值条件误命中 → 补漏被跳过 → 行数悄悄变少

`routers/templates.py::_fill_table_with_llm_fallback`

`_NUM_CMP_RE` 会命中任何 `>` `<` `≥`。用户写「按 GDP 降序，增速>5%」时，解析出 `keyword=增速`，模板里没有这一列，条件实际不生效；但 `numeric_filters` 非空这个事实，已经足以让代码把 `expected_row_count` 置空并 `skip_gap = True`——**补漏整段跳过，输出行数比应有的少，且没有任何提示**。

**修复**：新增 `usable_numeric_filters()`，先校验条件能否落到模板列上；一条都落不上就当没解析到条件，补漏照常进行。`apply_numeric_filters` 内部也补了同样的守卫。

### N5 · 空 `file_ids` 集合退化为「全库检索」

`services/vector_store.py::search`

```python
allowed = set(file_ids) if file_ids else None   # set() 是假值 → None → 不限
```

传空集合时语义是「不允许任何文件」，实际却变成「所有文件」。虽然当前唯一调用方在前面 `if not allowed_ids: raise` 挡住了，但这个函数是公开检索入口，语义陷阱迟早被踩。

**修复**：改为 `if file_ids is not None`，空集合就是空结果；`_tfidf_search` 内部同步改成 `is not None` 判断。

### N6 · 整列没有可解析数值时，把整张表清空

`services/data_filter.py::apply_numeric_filters`

多表 docx 模板里，某张表可能根本没有「GDP」列。此时该列全部解析失败 → 每一行都 `ok=False` → **整张表被删空**。这比不筛选更糟，且只在多表场景出现，很难在单表用例里发现。

**修复**：过滤前先探测该列是否存在可解析数值；整列都解析不出就跳过这条条件并记日志（`数值条件跳过: 列「X」在数据中没有可解析的数值`）。

## 五、需决策 / 后续（未改代码）

### P1 · 裸数字按表头单位直接写入，可能放大 1 万倍 —— 已解决，见 §六.1

`人均GDP（万元）` 列收到无单位裸数 `78661`（源文其实是「78661 元」）时，`normalize_cell` 判定「源值无单位 → 视为已是表头单位」，原样写入 `78661`。**量纲错了 1 万倍，且没有任何告警。**

这是「不猜口径」原则的必然代价，但原实现是**静默**的。已按「列级人工确认」方案改造：不再静默按表头单位吞掉，改为保留原值 + 登记待确认 + 用户决策后重填（详见 §六.1）。

### P2 · 两列表格永远走不到结构化路径

`data_filter.py::_enumerate_xlsx_header_candidate_rows` 要求表头行**至少 3 个非空标签**才作为候选。所以「城市 / GDP」这种两列表格永远匹配不上，一律落到 LLM 兜底——**慢、花钱、不确定**。

这是既有逻辑，改动会牵动表头识别（误判风险），本次不动。若演示里有两列模板，建议先确认走的是哪条路径。

### P3 · 向量检索是死代码，README 表述不实

`vector_store._ensure_embeddings()` **全仓无调用点**。`_embeddings` 只在它内部赋值，因此永远为 `None`，`search()` 恒走 TF-IDF 分支。

即使用户按 README 装了 `requirements-optional.txt` 里的 `sentence-transformers`，语义向量检索也**不会启用**。README 与评测材料里「sentence-transformers 向量检索，缺依赖时自动降级」的描述，与代码实际行为不符——评审若读代码会发现。

修法只有一行（`search()` 开头调用 `_ensure_embeddings()`），但会在装了依赖的机器上触发模型加载/下载，演示前改有卡顿风险，**留给团队决定**。

### P4 · 评测报告的 100% 准确率无法从仓库复现 —— 已解决，见 §六.2

`scripts/demo_testset_eval.py` 的 docstring 写明「准确率由 `scripts/demo_testset_score.py` 用源数据独立重算后比对」，但**该脚本不存在**于仓库。

报告 §一 强调「上表准确率全部由源文件独立重算后逐格比对得出」——这是材料里最有力的证据，却缺了产出它的工具。现已补齐评分脚本，并做了注入错误的负向验证（详见 §六.2）。

包含第三方来源数据（COVID-19 数据集、城市百强报告等）。提交前需确认：数据授权是否允许随仓库分发；14 MB 是否可接受。若不提交，评测报告里的复现路径会断。

## 六、本轮补充（按第一性原则重做）

### 六.1 单位口径：从「静默猜测」到「列级确认」

**问题本质**：源值 `78661` + 表头 `万元`，数据本身不含任何可区分「元 / 万元」的信号。任何自动决策都是猜，猜错就是 1 万倍量级错误。所以这不是解析能力问题，是**信息缺失**问题——解法不能是「猜得更准」，只能是「把不可判定显式化」。

**为什么是列级而不是单元格级**：一张 2570 行的表若逐格确认，会产出几千个确认框，产品上不可用。同一列在同一数据源里通常同口径，决策单元收敛到「列」才可操作。

**实现（四层，每层职责单一）**：

| 层 | 位置 | 行为 |
|---|---|---|
| 判定 | `unit_normalize.normalize_cell` | 源值无单位 且 表头声明了数量级 → **不做任何换算**，原值写入 + 告警 |
| 聚合 | `unit_normalize.collect_unit_confirmations` | 按列统计影响行数、样例值、两个候选口径 |
| 回放 | `unit_normalize.apply_unit_overrides` | 用户选定 `as_base` 时按倍率换算，`as_declared` 不动 |
| 透出 | `routers/templates._prepare_unit_confirmations` | 结构化路径与 LLM 兜底路径共用，返回 `unit_confirmations` |

**安全默认**：未确认时写**原值**（不篡改数值），同时结果页明确标注该列口径不可信。既不会写出错 1 万倍的数，也不会把整列清空导致不可用。

**API**：`POST /api/templates/{id}/fill` 新增可选 `unit_overrides: {"列名": "as_declared" | "as_base"}`；返回新增 `unit_confirmations[]`。前端在填写结果卡片内提供逐列单选 + 「应用并重填」，任务历史摘要标注「N 列单位口径待确认」。

**没有做的事**（有意）：
- 不自动猜「元 / 万元」——猜错代价 1 万倍；
- 不阻断填表——整表不可用比「带标记的可用结果」更差；
- 不做跨会话记忆——`TemplateInfo` 加字段需要 migration，线上已有库不会自动加列，风险高于收益。

### 六.2 评分脚本：`scripts/demo_testset_score.py`

不读被测系统的 `accuracy`（那只是列映射率），只用源文件重算：

| 用例 | 核验方式 | 本次结果 |
