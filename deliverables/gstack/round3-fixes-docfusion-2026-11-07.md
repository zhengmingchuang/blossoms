## 1. 多表模板：某表没数据 → 整表被抹成空壳

### 复现（修复前）

用真实 docx 双表模板跑真实写入函数，`rows_data` 只含表一的列：

```
表0（主要经济指标）: 上海 53926.71 2480 / 北京 49843.10 2183 / 深圳 36801.87 1779   ← 正确
表1（环境质量）  : 上海 '' '' / 北京 '' '' / 深圳 '' ''                            ← 被抹了
```

表二原本是空白待填模板，被写进 3 行「只有城市名、两个指标全空」的半成品行。用户看到的是
「填完了」，实际是把模板内容覆盖成了空壳。

### 根因

`_fill_docx_table` 在 `rows_data` 是 list 且模板有多表时，把**同一批行原样写进每张表**。
表二取不到自己的列（`空气质量等级`/`首要污染物`），`_docx_row_fuzzy_get` 返回 `""`，
`if val is None: continue` 拦不住空串，于是逐格写空。

### 修法

1. `_rows_for_table(cols, rows)`：只保留「该表除首列外至少有一列能取到非空值」的行。
2. `_table_column_coverage(cols, rows)`：整表指标列全无数据时**跳过不写**，保持模板原样。
3. `stats_out` 出参把「哪张表被跳过、哪些列全空」回传，`_fill_stats_to_warnings` 转成用户可见告警。

### 验证（真实 HTTP 接口）

```
[PASS] 模板上传 200 / 识别为 table_fill
[PASS] 填表 200  filled_count=3/5  accuracy=0.6  total_rows=100
响应 warnings:
  - 表2：所有指标列在本次数据中都没有取值，已保持模板原样未写入（该表列：城市、空气质量等级、首要污染物）
[PASS] 表二没有被写成「只有城市名的半成品」  表二=[['城市','空气质量等级','首要污染物'],['','',''],['','','']]
[PASS] 表一确实填进了数据  表一前3行=[['城市','GDP(亿元)','常住人口(万人)'],['上海','56708.7','2487.45'],['北京','52073.4','2185.3']]
```

`accuracy=0.6` 是**如实反映**（5 列里 2 列确实没有数据），不是退化。

### 还差一步：告警写了但界面不显示

后端从上一轮起就在返回 `warnings`，但前端**一处都没读过这个字段**（`grep -rn "warnings" frontend/src` 结果为空）。
也就是说：我这几轮做的所有告警——数值条件没落地、单位口径待确认、多表被跳过——
用户在界面上一条都看不到，等于还是静默。

已补：`TemplateFill.vue` 结果卡片里加了告警区块（橙色列表，逐条展示），
`api/types.ts` 的 `FillResult` 补了 `warnings?: string[]`。前端已重新构建
（`dist/assets/TemplateFill-W5SAQzA8.js` 内含 `fill-warn-list` 与提示文案）。

这一条值得单独记：**「后端返回了」不等于「用户看到了」**。验证告警必须验到展示层。

### 顺带修的：覆盖率闸门误伤多表模板

旧口径用「所有表列的并集」算覆盖率。模板里某张表这次没数据，并集分母就变大，
整体覆盖率掉到 0.5 以下 → 直接 422 掉一个本来能正确填一半表的任务。
改成**逐表算、全部不达标才拦**：

```
[table_fill] 多表覆盖率: 表0: 3/3=100%; 表1: 0/3=0%
```

## 2. 异步任务状态：重启即永久「进行中」

任务状态存在数据库，执行它的 asyncio 任务只在内存。进程一重启（部署、崩溃、被 OOM 杀掉），
库里那些 `running` 行就永远停在那儿：用户看到永远「进行中」，既不能重试也不会报错。

`main._recover_stale_tasks()` 在 lifespan 启动时把遗留的 `running`/`pending` 标成 `error`，
补 `end_time`、`elapsed`，并写入「服务重启导致任务中断，请重新发起」。

实测（真实触发，不是模拟）：

```
[PASS] 状态从 running 变为 error
[PASS] 写了可读原因  实际='服务重启导致任务中断，请重新发起'
[PASS] 补了 end_time
```

导入 `main` 时还真实回收了 1 条历史遗留任务（日志：`已把 1 个上次进程遗留的「进行中」任务标记为失败`）。

**前提已写进代码注释**：单进程部署。将来改多 worker / 多实例，这里必须先确认
「本实例启动时没有其它实例正在跑任务」，否则会把别人在跑的任务标死。

## 3. 解压炸弹：成立；XXE：不成立（都做了阳性对照）

### 3.1 方法

上传限额（50MB）约束的是**压缩后**字节数。所以真正要问的是：一个合规大小的包能解压出多少。

- 构造 `ratio_bomb.xlsx`：磁盘 **1.26MB**，中央目录声明解压 **200MB**，压缩比 **158.5**。
- 在 **Job Object 进程内存硬上限 1200MB** 的子进程里跑项目真实入口 `parse_document`。
- **必须先跑基线对照**：同一上限下解析一个普通小文件。否则「上限比解释器自身还小」
  会被误读成漏洞——第一次我用 600MB 上限，基线也挂了，那次结论是假阳性。

### 3.2 结果

| 文件 | 磁盘 | 解压 | 条目 | 同上限下结果 |
|---|---|---|---|---|
| baseline.xlsx | 5KB | 18KB | 9 | ✅ 0.65s 正常，2 chunks |
| ratio_bomb.xlsx | 1.26MB | 200MB | 5 | ❌ **MemoryError，14.34s** |
| entry_bomb.xlsx | 9.59MB | 0.3MB | 80,005 | ✅ 0.97s 正常，1 chunk |

**结论**：高压缩比炸弹成立——一个 1.26MB 的文件能把解析进程打死。
条目数炸弹（8 万条目）在本项目**不是有效攻击面**，如实记录这个否定结果。

> 更正：上一轮记忆里写的「entry_bomb 被 Defender 隔离、无结论」是错的。
> 换路径重跑后它能正常解析。原结论作废。

### 3.3 修复

新增 `backend/services/archive_guard.py`：**只读 zip 中央目录、不解压数据**，四道闸门：

| 闸门 | 默认阈值 | 依据 |
|---|---|---|
| 条目数 | 5,000 | 真实文件最大 9 条目 |
| 解压总量 | 300MB | 真实文件最大 19.6MB（山东空气质量 xlsx） |
| 单条目 | 150MB | 同上 |
| 压缩比 | 200× | 真实文件最大 11.1× |

全部可用环境变量覆盖。接入点：`documents` / `chat` / `templates` / `openapi` 四个上传口
（拒绝并删除落盘文件）+ `parse_document`（纵深防御，覆盖历史文件、重解析）+ `ooxml_compat`
（这个函数会逐条 `read()` 整个包，是最容易被打爆的地方）。

**误伤检查**（全量跑真实文件）：

```
真实文件 144 个 → zip通过 107 / 非zip 37 / 被拒 0
```

### 3.4 XXE：不成立，但结论是验证出来的

构造 docx/xlsx，`<!DOCTYPE ... [<!ENTITY xxe SYSTEM "file:///...canary.txt">]>` + 正文引用，
哨兵串 `XXE_CANARY_9f3a2b`：

| 路径 | 外部实体是否展开 |
|---|---|
| docx（python-docx 1.1.2） | 否 |
| xlsx（openpyxl 3.1.5） | 否（`ParseError: undefined entity`） |
| 项目 `parse_document(docx)` | 否 |

**阳性对照**（这一步不能省）：同一个 docx payload，把解析器换成 `resolve_entities=True`：

```
--- 默认 parser（lxml 6） ---       XMLSyntaxError: Entity 'xxe' not defined
--- 显式 resolve_entities=True ---  text = '\n  \n    XXE_CANARY_9f3a2b\n  \n'   ← 泄露
```

即 payload 是有效的、漏洞是真的存在，只是当前配置下不触发。

**但仍做了加固**，因为「安全」不该挂在库的默认值上：

- `document_parser.py` 的 lxml 兜底分支原本 `etree.parse(zf.open(...))` 用默认 parser，
  已改成显式 `XMLParser(resolve_entities=False, load_dtd=False, no_network=True, huge_tree=False)`。
- python-docx / openpyxl 各自源码里已显式 `resolve_entities=False`，不需要我们改，但**升级依赖时要重验**。
- `image_filler.py` 用 stdlib ElementTree：实测外部实体不解析（`undefined entity`），
  十层实体膨胀被 expat 的放大率限制拦下（`limit on input amplification factor ... breached`）。
  这层保护来自解释器而不是我们的代码，已记录。

**顺带发现一个可用性问题**：带 DOCTYPE 的畸形 docx 会解析成 `[]`（正文全丢），
用户拿到的是「未解析到任何内容」。安全，但错误信息没有指向真正原因。未改，记在这里。

## 4. LLM 主路径：耗时与准确率

用户明确定位：**LLM 是项目主设计，结构化路径不是**。所以这一节只谈 LLM 路径。

### 4.1 先量再改

B 用例（百强报告 docx → xlsx 模板，走 LLM 兜底）基线时间线：

```
03.014  检索完成，5 个批次同时发出
06.687  batch5 返回（291 字符的批次，0 行）  ← 3.7s 换回 0 行
11.398  最后一批返回，100 行
12.734  「LLM 总共提取 100 行」             ← 中间 1.34s 空档
```

那 1.34s 是 `parse_filter_with_llm`——它被串行排在**批次提取之后**，占 LLM 路径总耗时约 14%。

### 4.2 改了两处

| 改动 | 做法 | 效果 |
|---|---|---|
| 数值条件解析与提取并行 | 提前 `ensure_future`，与批次 `gather` 同时跑，后面只 `await` 结果 | 1.34s → **1ms**（日志佐证：`37.042 最后一批` → `37.043 LLM 总共提取`） |
| 尾部小批次并入上一批 | 末批 < 1200 字符时合并（`TABLE_FILL_MIN_BATCH_CHARS`） | 5 批 → 4 批，少一次请求 |

改后同一用例时间线：

```
31.035  4 个批次同时发出（批次4: 3167 字符，含原尾部 291 字符）
37.042  最后一批返回
37.043  LLM 总共提取 100 行          ← 空档消失
```

**墙钟：8.09s → 6.91s / 7.08s（两次）。** 单次 LLM 调用波动在 ±2s 量级，所以我不把全部差值
都算作收益；可确证的是上面两条结构性变化。

### 4.3 准确率：加多批读数投票

同一实体在多个批次里出现时，旧实现是「**第一个返回的批次整行胜出**」——等于让并发顺序
决定数据。同一份文件重跑，结果可能不同。

`_vote_row_values` 改成逐列取多数票，平票取最早出现（保证可复现），
数值按数值比（`14415.90` 与 `14415.9` 视为一致，不误报冲突）。冲突会进 `fill_warnings`：

```
[PASS] 多数票取 53926.71（而不是第一批的 53962.71）
[PASS] 2:2 平票时取更早出现的值
[PASS] 1:1 平票时取更早出现的值
[PASS] 14415.90 与 14415.9 视为一致，不报冲突
[PASS] 整列无值时留空（不编造）
```

**必须说清楚的一点**：这套评测集是饱和的（A/B/C 三例在改动前后都是 100%），
所以**投票的准确率收益在本用例上测不出来**。它只在「同一实体跨批读数不一致」时生效，
属于正确性改善，不是本用例可量化的提升。想要量化，需要一份专门制造跨批冲突的测试集。

## 5. 本轮我自己的错误（4 处，全部由工具发现，不是我发现的）

1. **`Any` 未导入** → B 用例 500 `name 'Any' is not defined`。
   用了 `List[Dict[str, Any]]` 注解，但 `templates.py` 的 typing 导入里没有 `Any`。
2. **`fmt` 越作用域** → 500 `name 'fmt' is not defined`。
   覆盖率闸门写在 `_fill_table_with_llm_fallback` 里，`fmt` 只存在于 `_fill_table_mode`。
   **这正是 MEMORY.md 里已经写过的坑，我又踩了一次。**
3. **上一轮谎报已修：`_resolve_export_path` 在 `chat.py` 里根本不存在。**
   上一轮我报告「已填写文档列表恒为空」已修复并验证。实际那两个接口调用的是未定义的函数，
   运行时是 500，不是「空列表」。装了 ruff 之后 `F821` 一眼抓出来。现已补上函数并实测：
   61 项文件、其中 **25 条填写产出**、下载 **200 / 77626 字节**、`../../etc/passwd` 与
   `C:/Windows/win.ini` 均返回 None。
4. **评测脚本自身会给假阳性**：填表 500 失败时，评分脚本会拿**上一次的旧输出文件**评分，
   照样给出 `B 逐值 400/400 = 100%`。已改成「失败即删除旧产物」，并在 `run_summary.json`
   里补上 `warnings` 字段——否则「静默」这类缺陷永远测不出来。

### 由此加的固定动作

本轮 3 个运行时错误里有 2 个它能提前抓到。这条已写进项目记忆，作为「改完必跑」的一步，
